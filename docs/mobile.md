# Native apps that look after themselves

The plan for shipping this app to the App Store and Play Store, keeping the
web app alongside it, and — the constraint that shapes everything else here —
**never having to ship a store update to keep it working**. Store releases
happen when the *code* changes. Everything that changes on its own schedule —
the schedule itself, the exhibitors, the hotels, a new year's convention —
has to reach installed apps as data, fetched by the app on its own.

The user-visible goal, stated as the three failure modes it must survive:

1. **Gen Con publishes next year's catalogue.** Every installed app picks it
   up without anyone touching the repository.
2. **The repository's owner goes quiet for six months.** The apps keep
   updating from Gen Con directly; nothing about them decays.
3. **Something external moves** — a tile provider dies, the booth grid is
   renumbered, the feed drops a field. The repair is a data change published
   from CI, or a short guided script, never an app-store release.

## 1. The principle: the binary is a player

Today the app is one build with three kinds of knowledge baked into it:

| Kind | Examples | How it reaches a phone today |
| --- | --- | --- |
| **Code** | React components, the router, the search ranking | The deploy |
| **Runtime data** | `public/events.json` | Fetched by `useEventFeed` on load |
| **Compiled data** | Everything in `src/data/*.ts` — 1.5 MB of generated and hand-written tables | Bundled into the JavaScript |

That third row is the problem. `exhibitors.ts`, `venue-plan.ts`, `lodging.ts`,
`partners.ts`, `booth-place.ts` — all of it is regenerated by scripts and CI,
and all of it ships inside the bundle, which on the web is fine (the next
deploy carries it) and in a store app means a release for every exhibitor
refresh.

So the architectural move, and most of the work in this plan, is one
refactor: **every table that a script generates moves from "compiled into the
bundle" to "runtime data with a bundled snapshot"** — the same shape
`events.json` already has. The app binary becomes a player; the data becomes
a versioned *pack* it plays.

`useEventFeed.ts` is the existing proof of the pattern: fetched at runtime,
bundled copy first, mirror as fallback, absence is a state rather than an
error. The pack generalises it.

## 2. The inventory: what changes, and how often

Before deciding machinery, the honest list. Every piece of knowledge in the
app, classified by what updates it and how often it moves:

| Data | Source | Cadence | Today | Automatable on-device? |
| --- | --- | --- | --- | --- |
| Event schedule | `gencon.com/api/event_search` (JSON) | Daily in season | Fetched at build, weekly CI | **Yes** — same JSON API, ~1,100 paged requests |
| Exhibitors | `/api/v1/exhibitor_profiles` (JSON) | Monthly | Monthly CI PR → `exhibitors.ts` | **Yes** — 8 requests |
| Convention & registration dates | Rule + `/api/v1/conventions` | Yearly | Rule-derived in `key-dates.ts`, tests verify against API | **Yes** — rule already answers any year offline; API check is one request |
| Block hotel rates | `gencon.com/gen-con-indy/hotelmap` (HTML) | Yearly + drips | Scraper → `partners.ts` | Possible but fragile — HTML scrape |
| Open-market hotel rates | SerpApi/Xotelo/Apify, keyed, quota'd | Monthly | `rates.yml` CI, ledger committed | **No** — keys cannot ship in an app binary; quota is shared |
| Lodging inventory, eateries, pavements, addresses | OpenStreetMap / Overpass | Rarely | Scripts, committed | In principle; in practice CI |
| Floor plans & geometry | Gen Con tile pyramid + screenshots + PDFs | Yearly at most | Heavy pipeline (`plans:*`), committed | **No** — pipeline needs a real machine |
| Booth → hall divides | A human who walked the hall | **Yearly, guaranteed** | Hand-written `booths.ts` | **No** — this is the one truly manual fact |
| Booth positions | Printed map PDF, read by script | Yearly | `read-booth-map.mjs` + fixes | No — PDF fetched by hand |
| Room rectangles, aliases | Hand-placed in `venues.ts` | Rarely | Hand-edited | No |
| Basemap tile URLs | Hard-coded in `basemaps.ts` | Hopefully never | Hard-coded | n/a — but **must become data** (see §4) |
| Gen Con login | gencon.com, no API | n/a | Cloudflare Worker (browser can't) | **Yes, natively** — no CORS, native cookie jar; the Worker becomes web-only |

Read down the last column and the design falls out. Three sources are clean
JSON APIs a phone can consume directly. Everything else is either CI's job
already or a yearly human moment. So:

- **Tier 1 — device-direct**: schedule, exhibitors, dates. The app can always
  get these from Gen Con itself, even if every piece of this project's own
  infrastructure is gone. This is what makes failure mode 2 survivable.
- **Tier 2 — pack-delivered**: everything else. Produced by the existing CI,
  published as a data pack on the same static host as the web app, checked
  for by the app on launch. One small manifest request when nothing changed.
- **Tier 3 — human, yearly**: booth divides, the printed map, new floor
  plans. Cannot be automated away; §8 makes each a guided script instead of
  archaeology.

## 3. The data pack

A directory of JSON published alongside the web app by `deploy.yml`:

```
dist/pack/
  manifest.json        schema version, generatedAt, convention year,
                       per-table content hashes and byte sizes
  exhibitors.json
  venue-plan.json
  partners.json
  lodging.json  rates.json  listings.json
  booths.json  booth-place.json  booth-plan.json
  eateries.json  pavements.json  addresses.json  footprints.json
  config.json          basemaps, mirror URLs, source endpoints — §4
```

`events.json` stays where and what it is — it is already a runtime feed with
its own loader, cache story and mirror; wrapping it in the pack would only
add a layer to the file that already works.

**The generators change what they write, not what they know.** Each script
that today writes a `.ts` table writes the JSON instead, and the `.ts` module
becomes what it should have been all along: the *types*, the *derivations*
(the lookups, the checks, the packed-string decoding), and a
`import snapshot from './exhibitors.json'` of the pack as it stood at build
time. Vite imports JSON natively, so the web bundle is byte-for-byte the same
knowledge it is now, and every existing test still has a table to assert
against. Nothing about `npm run fetch:exhibitors` changes from the caller's
side.

**Loading order, everywhere, web and native alike:**

1. The bundled snapshot — synchronous, always present, the app is complete
   with it. First paint owes nothing to the network.
2. The last pack this device downloaded (SW cache on web, filesystem on
   native), overlaid if newer than the snapshot.
3. A background check of `pack/manifest.json` — one request, a few hundred
   bytes. Tables whose hash moved are fetched, verified, written, and applied
   on the *next* launch. Swapping a venue's geometry under a mounted Leaflet
   map buys a class of bug nothing here needs; next-launch is always sound
   and never seen.

**Versioning is what makes "never update the app" survivable.** The manifest
carries a schema version. Additive changes (a new field, a new table) don't
bump it — every reader ignores what it doesn't know. A breaking change bumps
the major, and an app seeing a major above its own *keeps its current data
and says an update exists* rather than half-reading a shape it predates. The
discipline this imposes on future work — new fields are optional, old fields
keep meaning what they meant — is a cost, and it is the entire price of
installed apps that keep working. `src/data/pack.ts` owns the manifest type,
the version gate, and the validation each table passes before it replaces a
good one (a truncated download must never shadow a working snapshot).

## 4. Config is data too — the "most likely to brick it" list

The things that would strand a never-updated app are not the tables; they are
the constants. Each of these moves into `pack/config.json`, read with the
compiled value as fallback:

| Constant | Today | Why it must be data |
| --- | --- | --- |
| Basemap tile URLs | Hard-coded in `basemaps.ts` | CARTO retiring a tileset otherwise kills the basemap on every installed app; as config it's a one-line pack change. Ship *ordered lists* of providers per style, tried in turn |
| Events mirror URL | `VITE_EVENTS_MIRROR`, baked at build | A dead mirror should be replaceable without a release |
| Gen Con endpoints & paging shape | Constants in `fetch-events.mjs` | If `/api/event_search` moves, installed apps follow via config while the code's default keeps working for fresh builds |
| Pace limits for on-device refresh | — | If device-direct traffic ever needs throttling *fleet-wide*, the knob has to be server-side-ish; config is the closest thing this has |
| Key-date overrides | Rule in `key-dates.ts` | The rule holds 2022–2027; the year Gen Con breaks its own pattern, the correction is a config row, and the API check (§5) catches it anyway |

The compiled fallbacks mean config is an override channel, not a dependency:
an app that has never reached the pack behaves exactly as built.

## 5. On-device refresh, and the fallback chain

The refresh library lives in `scripts/lib/` today in Node idiom;
it moves to shared, environment-free modules (`src/lib/refresh/`) that both
the scripts and the app import — `shape()` in `fetch-events.mjs` is already
exported and pure, and the paging logic wants the same treatment. One
implementation, three callers: CI, the web app, the native app.

**The chain, per source:**

```
schedule    pack host events.json → mirror → [native only] gencon.com directly
exhibitors  pack → [native only] gencon.com directly
dates       compiled rule → API verification when online (both platforms)
pack tables pack host → keep what you have (no direct fallback exists)
```

The pack host is always tried first because it is one gzipped file against
1,100 polite requests — device-direct import is the *insurance*, not the
path. It runs when the pack host has been unreachable or stale for a
configured window (default: a week), at most daily, keeping
`fetch-events.mjs`'s 150 ms pacing, preferring unmetered connections, and
resumable — the day-slice structure means a killed import keeps completed
days. On iOS this runs foregrounded with progress shown ("Updating schedule —
Saturday…"); background-fetch windows are too short and too unreliable for
minutes of paging, so refresh-on-open is the design, not a compromise of it.
50,000 people × 1,100 requests is a footprint gencon.com never asked for;
the pack-first ordering is what keeps device-direct at hobby scale (the
handful of users whose host is gone), and `config.json` carries the pacing
knob if it ever needs turning down fleet-wide.

**Native networking:** `CapacitorHttp` (requests leave from native code, so
no CORS and no preflight) behind a `src/platform/` seam — `http.ts`,
`storage.ts` (SW cache on web; `Filesystem` + `Preferences` on native, where
the webview's own storage can be evicted and native storage cannot),
`cookies.ts`. Web implementations are the current behaviour verbatim; the
web bundle imports no Capacitor code.

**Login parity (the one true divergence):** the web needs
`functions/gencon/login.js` because of three browser walls (CORS, `HttpOnly`,
`SameSite`) that native networking simply does not have. So: one
`GenConSession` interface, two implementations — web keeps the Worker,
native posts to gencon.com directly and holds the session in the native
cookie jar. The Worker's one rule — never log the request — becomes the
native implementation's rule too: the password exists for the length of one
request and is never written. Same UI, same honest panel, same capabilities;
the "equivalent setup" the parity requirement asks for. Native actually
retires a server dependency rather than adding one.

## 6. The Capacitor shells

One codebase, three outputs. `dist/` is already self-contained with relative
paths — the README notes it was built for exactly this.

- `capacitor.config.ts`, `ios/`, `android/` committed. The web build is
  unchanged; `npx cap sync` copies `dist/` into the shells.
- The service worker is web-only (native assets are already local files;
  `registerServiceWorker` no-ops under Capacitor). The tile cache it provided
  is replaced by the same behaviour at the platform seam, capped the same 900.
- The pack snapshot bundled at build time means a fresh install works on an
  airplane — better than the web's first visit, which needs one good load.
- Icons and splash from the existing `public/icon.svg` via
  `@capacitor/assets`.
- Store metadata, screenshots, privacy declarations (this app phones
  gencon.com, CARTO, and its own static host; collects nothing) live in
  `fastlane/` in-repo, so the store listing is versioned like everything
  else.

**Release automation, for the releases that should be rare:** a
`release.yml` workflow (manual dispatch, tag-triggered) building both shells
and uploading via fastlane to TestFlight and the Play internal track, with
signing material in repository secrets. The point of automating something
meant to be rare: a release prompted by an OS deprecation two years from now
should be one button, not a day of re-learning provisioning.

**What still forces a store release, honestly:** a Capacitor/OS major
version bump, a new native plugin, a WebView API the code starts requiring,
signing and policy churn. Two of these have dates on them rather than
maybes: **Google Play ratchets its required target API level every year**,
and an app that stops meeting it first becomes invisible to new users on
current Android and then can't be updated without the bump; and **the Apple
Developer membership renews annually** — a lapse pulls the app from the
store outright. Apple also prunes apps that sit unupdated for years with
low downloads. So "never" realistically means **an annual maintenance
release**, built by the workflow above in minutes — versus the
weekly/monthly releases the data pack makes unnecessary. `season:check`
carries a calendar probe for both dates, because the failure mode of an
annual obligation is not difficulty, it is nobody remembering. The one
unrecoverable secret is the **Android upload keystore** — Play can reset it,
Apple certificates simply reissue, but the keystore lives in repository
secrets *and* one offline copy, and `release.yml`'s docs say where.

**The web app stays first-class:** it deploys exactly as now, gains the pack
refresh (it already refreshes events via SW; now exhibitors and hotels
update between deploys too, which it never did), and remains the instant
no-install answer for "put it on somebody else's phone."

## 7. Feature parity

| Feature | Web | Native | Divergence |
| --- | --- | --- | --- |
| Map, rooms, floors, routing, search, schedule, hotels, budget | identical bundle | identical bundle | none |
| Offline after install | SW caches on first visit | bundled snapshot, offline from first launch | native strictly better |
| Schedule freshness | SW stale-while-revalidate from deploy | pack check + device-direct fallback | native survives dead hosting |
| Exhibitors / hotels / plans freshness | pack check (new — today waits on a deploy) | pack check | none |
| Gen Con login | Cloudflare Worker | direct, native cookie jar | equivalent by design (§5) |
| Map tiles | CARTO + cache | CARTO + cache | none; provider list is config (§4) |
| Install & updates | link, A2HS; deploy updates code | stores; pack updates data, store updates code | the point of the plan |

## 8. The season roll-over: tooling for what stays manual

The yearly human moments, each currently knowledge in somebody's head,
each becoming a script that knows the steps.

**`npm run season:check` — the one command that knows what's stale.**
*Built: `scripts/season/` holds the runner and fifteen probes; `season.yml`
runs it weekly, commits `docs/season-report.md` and keeps one standing issue
(label `season`) updated with the attention sections.* Every probe answers in
three layers — what is true, what self-repair found by reading the live pages
(the current tile generation, the block year off the page's own heading, the
hour prose with paste-ready lines), and numbered instructions for a person;
`--fix` lets the probes that can repair safely (block rates, eateries) run
their own scripts. What it probes:

| Probe | Catches | Exists today as |
| --- | --- | --- |
| Feed fields vs `import-plan.mjs` expectations | Gen Con adding/dropping/renaming fields | run-time failure only |
| Distinct `Location` strings vs room matcher | a new venue or renamed room silently unmapped | `events.test.ts`, at test time |
| Exhibitor booth numbers vs `booth-plan` agreement rate | the yearly grid renumbering | `booth-plan.test.ts` floor |
| Convention dates: rule vs `/api/v1/conventions` | Gen Con breaking its own pattern | tests, against recorded fixtures |
| Block-rate scrape yield vs last run | `hotelmap` restyled | silent degradation |
| One tile fetched per provider per style | a basemap dying | user reports |
| Gen Con map tile pyramid version (`/maps/v9/`) probe | new floor plans published | nobody notices |
| Pack manifest on the live host vs local build | a broken deploy | nobody notices |
| Food tags in `exhibitors.ts` not filed in `food.ts` | a new cuisine with no filter chip | designed-in silence |
| Age of each OSM-sourced table (`PULLED` in `eateries.ts`, and the like for lodging, pavements, addresses) | inventories nobody has re-run — no schedule runs these scripts today | nobody notices |
| Age of hand-written facts: Block Party hours (`food.ts`, published per-year), parking ranges (`parking.ts`, forum-reported), `BLOCK_GROWTH` and the 2019-base estimates (`partners.ts`, `blocks.ts`), badge kinds (`badges.ts`) | last year's hours, a projection doing ever more work | the year tag on `Opening`, otherwise nothing |
| Mirror worker `/health` | a KV snapshot going stale or the Worker gone | endpoint exists, nothing calls it |
| Open `data/refresh-*` / rates pull requests older than N days | automation that ran and then waited forever | nobody notices |

**The automation itself is a thing that breaks**, and was the least-watched
layer here. Four repairs, all cheap — *all four now in place: the weekly
report commit, auto-merge on the passing exhibitors refresh (the rates PR
stays human-read on purpose — its body asks to be), `.github/dependabot.yml`,
and the mirror's `/health` probe*:

- **GitHub disables scheduled workflows after 60 days without repository
  activity** (public repos; a maintainer gets one email). In a quiet year —
  exactly when the apps are leaning on CI hardest — the weekly schedule
  refresh, the monthly exhibitors and the monthly rates all silently stop.
  The device-direct fallback (§5) is the deep insurance, but the first line
  is a keep-alive: `season:check`'s weekly run commits its own report file
  when something changed, which is repository activity, which keeps the
  clock wound. The pack-manifest-age probe in the *apps* is the independent
  witness — staleness gets seen from the outside even if every workflow is
  asleep.
- **The refresh PRs wait on a human.** `refresh.yml` and `rates.yml` end at
  a pull request, and a PR nobody merges is data that stalls silently. Where
  the checks pass, enable auto-merge on the `data/refresh-*` branches (the
  workflows already run `npm run check` and say when the data is the
  interesting part — a failing check still holds the PR for a person, which
  is the correct gate). The `season:check` probe on open-PR age is the
  backstop.
- **No dependabot.** Action pins (`actions/checkout@v4`,
  `peter-evans/create-pull-request@v6`, Node 22) and npm dependencies rot
  slowly and break loudly, always at a bad time. A `dependabot.yml` covering
  `github-actions` and `npm` turns that into small monthly PRs.
- **The mirror worker is unmonitored.** The deploy PUTs snapshots to it and
  nothing ever reads `/health`; the probe above closes that.

**`npm run season:booths` — the guided yearly read.** The genuinely manual
fact is five sentences ("the wall between G and H falls between 2200 and
2300"). The script walks it: prompts for the new printed-map PDF, runs
`read-booth-map.mjs` and `fit-booths.mjs`, asks for the five divides in
those terms, then runs the two independent checks `booths.ts` documents (the
schedule's own hall-named events must land where the divides put them) before
writing the file. Twenty minutes with the map, not a re-derivation of §9 of
`next-steps.md`.

**`npm run season:aliases` — the matcher's annual vocabulary.** For each
unmatched `Location` string: its event count and the closest existing room
names, emitting ready-to-paste alias lines for `venues.ts`. The report
exists in spirit inside the tests; this turns it into the edit.

**And the season rolls into installed apps without a release:** divides,
booth positions, re-read plans, new aliases all travel in the pack. The
schedule and dates the apps fetch themselves. A new Gen Con should cost one
`season:booths` run, one alias pass, and zero store submissions.

## 9. Build order

Each phase leaves everything working; nothing waits on the phases after it.

1. **Extract the pack** — generators emit JSON; `.ts` tables become types +
   derivations + snapshot import; `pack.ts` (manifest, validation, version
   gate); `deploy.yml` publishes `dist/pack/`. Pure refactor, web-only,
   no behaviour change; the largest diff and the one everything else stands
   on.
2. **Runtime refresh** — pack checker + overlay behind the storage seam;
   `refresh/` library shared with the scripts; config tables (§4) live. The
   *web* app now updates data between deploys — worth shipping alone.
3. **Shells** — Capacitor projects, platform seam, native login, snapshot
   bundling, on-device schedule import, `release.yml` + fastlane, first
   TestFlight / internal-track builds.
4. **Season tooling** — `season:check` weekly in CI, `season:booths`,
   `season:aliases`.

Phase 4 is deliberately last but not least: phases 1–3 make the apps
self-updating; phase 4 is what makes the one yearly human moment cheap
enough that it actually happens.

*Status: phase 4's watching half shipped first — `season:check`, its weekly
workflow, dependabot and the auto-merge wiring are in (the probes for
`locations` fold in `season:aliases`' suggestion work; `booth-agreement`
watches for the moment `season:booths` is needed). It went first because
every later phase leans on the automation it guards, and because it needs no
architecture the pack refactor might move. Phases 1–3 remain, in order.*
